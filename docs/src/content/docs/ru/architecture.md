# Архитектура

Sharptown — это монорепозиторий на pnpm, построенный вокруг одного принципа: **вся работа с
изображениями живёт в едином движке, не зависящем от фреймворка, а каждый транспорт — это
тонкий адаптер поверх него.**

## Общая картина

```
                ┌─────────────────────────────┐
                │      @sharptown/core         │
                │   Движок Sharp (libvips)     │
                │  applyOperations / transform │
                └──────────────┬──────────────┘
                               │ используется каждым адаптером
        ┌──────────────────────┼──────────────────────┐
        │                      │                       │
┌───────▼────────┐   ┌─────────▼─────────┐   ┌─────────▼──────────┐
│ @sharptown/    │   │ @sharptown/       │   │ @sharptown/        │
│   fastify      │   │   server-grpc     │   │  server-jsonrpc    │
│ REST-плагин    │   │ streaming-хост    │   │ WS JSON-RPC хост    │
└───────┬────────┘   └───────────────────┘   └────────────────────┘
        │
┌───────▼────────┐                         ┌────────────────────┐
│ @sharptown/    │   ◀──── HTTP ────▶       │  @sharptown/client │
│  server-rest   │                         │  изоморфный JS     │
└────────────────┘                         └────────────────────┘
```

## Движок-ядро — `@sharptown/core`

Сердце проекта. Он не зависит **ни от одного веб-фреймворка**; он просто умеет управлять
Sharp. Две точки входа покрывают оба стиля обработки:

- **`transformBuffer(input, options)`** — трансформирует буфер в памяти и возвращает
  `{ data, format, contentType }`. Используется REST и JSON-RPC.
- **`createTransformStream(options)`** — возвращает дуплексный поток Sharp, настроенный
  под файлы любого размера (`sequentialRead`, без лимита на входные пиксели). Используется
  gRPC.

Оба проходят через **`applyOperations(image, options)`** — единственную функцию, которая
сопоставляет ваши параметры (`width`, `blur`, `convertTo`, …) с вызовами Sharp. Поскольку
её переиспользует каждый адаптер, поведение идентично, к какому бы транспорту вы ни
обратились.

```js
import { transformBuffer } from '@sharptown/core'

const { data, contentType } = await transformBuffer(inputBuffer, {
  width: 800,
  convertTo: 'webp',
})
```

Некорректные значения порождают **`InvalidOperationError`**, который каждый адаптер
отображает в собственное соглашение об ошибках (HTTP 400, gRPC `INVALID_ARGUMENT`,
JSON-RPC `-32602`).

## Транспортные адаптеры

| Адаптер | Стиль | Лучше всего для |
| ------- | ----- | --------------- |
| **REST** (`@sharptown/fastify-plugin` → `server-rest`) | `multipart`-загрузка, бинарный ответ | Веб-приложения, CDN, `curl`, JS-клиент. |
| **gRPC** (`server-grpc`) | Двунаправленный стриминг | Огромные файлы, межсервисное взаимодействие, backpressure. |
| **JSON-RPC** (`server-jsonrpc`) | JSON-RPC 2.0 поверх WebSocket, base64 | Приложения с постоянным сокетом, батчинг, уведомления. |

Каждый адаптер мал именно потому, что настоящую работу делает ядро. Добавить новый (Hono,
Elysia, Express…) значит: прочитать вход, вызвать `transformBuffer`, отправить байты,
сопоставить `InvalidOperationError` с ошибкой.

## Клиент — `@sharptown/client`

Изоморфный JS-клиент, работающий в браузере, Node, Bun и Deno. По умолчанию он говорит на
REST-транспорте, но имеет **подключаемый интерфейс транспорта**, так что позже можно
добавить другие. См. [JS-клиент](/ru/docs/js-client).

## Решения, о которых стоит знать

- **Самодокументируемый код, JSDoc на публичном API.** У каждой экспортируемой функции есть
  `@example`.
- **Стриминг никогда не буферизирует файл целиком.** Путь gRPC прокачивает чанки прямо в
  Sharp и обратно, поэтому память остаётся плоской даже для многогигабайтных входов.
- **Определение формата по выходу самого Sharp.** Заголовок `Content-Type` корректен, даже
  если вы не передали `convertTo`.
